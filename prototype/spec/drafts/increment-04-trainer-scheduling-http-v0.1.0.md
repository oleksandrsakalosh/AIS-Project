## 1. Scope and responsibilities

An active Trainer with an effective catalog link can publish one future training at a time, edit their own future session details where reservation history permits, and set its capacity. The shared schedule shows committed changes on the next read. Client booking and cancellation continue under the approved booking rules. The local scope covers single sessions in the Slovak web app. Substitution, recurring sessions, training removal or staff cancellation, spreadsheet import, payments, and notification delivery are deferred. R-06 training-change notices belong to INC-07, with DEC-C07 pending. INC-04 saves training state and create receipts only, with no notice records or delivery side effects. ### Common behavior for new JSON routes

Use same-origin `poc_session`, `Cache-Control: no-store` on the editor page and JSON responses, and `X-CSRF-Token` from `GET /session` for writes. Check in order `401 unauthorized` for missing, expired, disabled or revoked sessions, `403 forbidden` for an active role other than `trainer`, `403 trainer_link_required` for a Trainer without an effective link, then `403 csrf_invalid` on a write. Apply `422 validation` next for malformed input, including malformed UTF-8/JSON, wrong media type, missing or extra body fields, invalid IDs and invalid field values. Apply the operation-specific checks below in order. Use `{"error":{"code":"…","message":"…"}}` with sanitized messages. Known storage unavailability, including exhausted lock waits, returns `503 storage_unavailable`. Other unexpected failures return sanitized `500 internal_error`. A failed transaction rolls back all changes. A missing response can leave the client uncertain about a committed write.

IDs, `capacity` and `expected_version` are positive integers through `9007199254740991`. JSON strings, fractions and booleans are invalid integer inputs. Path IDs use decimal digits. `request_id` is a canonical lowercase hyphenated UUIDv4. Writes accept `application/json` and only the listed fields. `starts_at` and `ends_at` are UTC RFC 3339 strings of the form `YYYY-MM-DDTHH:mm:ss[.ffffff]Z` with zero or one to six fractional digits. Require valid calendar instants and `ends_at > starts_at`. Responses use the existing UTC serialization. The browser collects wall time in `Europe/Bratislava` independently of device time zone. A spring-forward gap requires a corrected time. For the repeated autumn hour, require the user to choose the displayed offset for each ambiguous value before submitting. Preserve the matching offset and full instant for unchanged times loaded into an edit form.

**Editor response models.** `TrainingEditorItem` contains `id_treningu`, `trainer_id`, `trener`, `activity_id`, `aktivita`, `room_id`, `priestor`, `starts_at`, `ends_at`, `capacity`, `obsadene`, `volne_miesta`, `version` and `has_reservation_history` (boolean). Counts are derived from confirmed reservations. History is true when any reservation row exists. Labels are current at the snapshot used for the response, except a create replay returns its original snapshot. Editor data excludes clients, reservation IDs, account details and catalog versions.

## 4. State, duplicates and concurrent writes

- **BR-S01 · Ownership and fresh state.** Resolve identity from the current session and the explicit INC-03 link. An effective link requires an active Trainer account and an active trainer record. Reauthorize mutations inside the shared write transaction before applying business rules, including the current CSRF context and link. A read authorized in its snapshot can finish if access is revoked afterwards. Resolve the target by ID and trainer together so the error for someone else’s training reveals no edit state. Recheck catalog status in the transaction for both creates and edits. First binding through INC-03 can give a Trainer access to their existing future classes. [INC-03 link policy](increment-03-catalog-administration-http-v0.1.0.md#4-state-retries-and-simultaneous-actions)
- **BR-S02 · Time and allocation.** Use a fresh server UTC clock after acquisition or retry of the write transaction. Recheck time immediately before a real write. A future start is strictly greater than the sampled time. Compare instants, including for no-op recognition, and check half-open intervals `[start,end)`. Another row overlaps if `candidate.start < other.end` and `other.start < candidate.end`. Block overlap with any scheduled training that shares either the trainer or the room, regardless of its bookings or trainer link. Exclude the edited row itself. Check overlap for creation and edits changing start, end or room. Exact adjacency and simultaneous sessions with distinct trainers and rooms are allowed. Any existing overlap predating this increment stays readable. A capacity-only or activity-only edit may proceed if it passes its other rules, and an allocation edit must resolve the edited training’s overlaps. Capacity is per training under the DEC-C03 recommendation.
- **BR-S03 · Reservation history and capacity.** The first reservation commit locks the training’s start, end, activity ID and room ID for the life of that row, including after all reservations are cancelled. The assigned trainer is always fixed in this contract. Cancellation releases one seat but keeps the history lock. For a future training, allow capacity at or above the current confirmed count with a minimum of one. A change to capacity never alters reservations. At the exact start all edits are refused, including a would-be no-op. Catalog rename behavior under DEC-C10 still uses current display labels on schedule and history. [Booking capacity and cancellation rules](../prototype.md#deterministic-processing-and-repeats) · [DEC-C10 approval](increment-03-catalog-administration-http-v0.1.0.md#7-approval)
- **BR-S04 · Repeats and recovery.** Scope a create receipt to `(account_id, request_id)` and retain it for the local database’s lifetime. Store the resolved trainer ID, normalized create fields (compare UTC instants) and original response with the training record. An exact replay with current authorization and the same effective trainer can succeed after edits or start and performs no write. A refused attempt stores no receipt. Simultaneous same-key requests with the same input save one training and return the same receipt. Different keys represent separate attempts and still face overlap checks. Real edits from the same version permit one commit. A repeat with an old version gives `training_changed` if the actor and target still qualify for access. Occupancy, calendar clock and catalog renames leave the training version intact.

  The browser retains an unresolved create key and its original normalized input across reloads in the same signed-in browser context, scoped to account and trainer. After an uncertain save, refresh the editor first. Offer explicit replay of the original create even if the list contains a similar row. Clear the pending intent after a definitive result or an explicit abandonment after refresh. Refresh again after receiving a recovered receipt. For an uncertain edit, compare the row’s current values and version and show what the read establishes about current state. If the row has left the editor’s future list, show that the save could not be verified. When refresh fails, hold further saves until it succeeds. Require an explicit action for another submission and confine each pending create to its original account and trainer.
- **BR-S05 · Shared transaction and outcomes.** Serialize scheduling, account, catalog and reservation writes against the same SQLite store. Authorization, future references, versions, intervals, history and confirmed counts must be consistent with the committing transaction. If booking wins against a details edit, the edit returns `training_details_locked`. If the edit wins, the v0.1.1 booking contract uses the revised training after checking eligibility and capacity. Under DEC-C14 there is still a window after the browser refresh in which this can happen. If a capacity reduction wins, a later booking that would exceed it gets `capacity_full`. If the booking wins and takes occupancy above the requested capacity, the reduction gets `capacity_below_occupancy`. If cancellation wins and lowers occupancy enough, the reduction can succeed. Cancellation racing a details edit never clears the history lock. When scheduling establishes a future catalog reference first, subsequent deactivation of its activity, room or trainer returns `future_training_reference` while the reference is future. If activity or room deactivation wins, scheduling refuses the inactive ID. A trainer’s first future assignment also triggers `future_training_assignment` for subsequent attempts to remove or replace the existing link, disable the account or move it away from Trainer. If unlink or trainer record deactivation wins first, the queued scheduling write gets `trainer_link_required`. If disable or role change wins first, the revoked session receives `unauthorized`. A first link that commits before the editor read or write makes its trainer assignments available to the linked account. Two otherwise valid overlapping saves allow only one allocation. [INC-02 transaction rules](increment-02-account-administration-http-v0.1.0.md#5-rules-repetitions-and-concurrent-actions) · [INC-03 transaction rules](increment-03-catalog-administration-http-v0.1.0.md#4-state-retries-and-simultaneous-actions)
- **BR-S06 · Local upgrade and persistence.** Extend the existing explicit `python -m app.migrate [--db <path>]` path from schema 0.4.0 and retain supported earlier upgrades. Backfill version 1 for existing trainings and derive history/occupancy from existing reservations. Preserve IDs, UTC instants, capacities, catalog links, references, reservations, accounts, memberships and eligible sessions. Check existing intervals and occupancy as part of upgrade verification. Preserve legacy overlaps as described above. If data cannot satisfy basic invariants such as valid intervals, positive capacity, confirmed count at or below capacity, or valid references, report a safe migration failure with the prior database intact. An unavailable, missing, foreign or unsupported database fails safely. Repeat migration and normal initialization preserve data. Only explicit demo reset removes local edits and receipts and restores the existing fictional fixtures, including unlinked trainers. [Local database lifecycle](../../README.md#dáta-reštart-a-reset)
