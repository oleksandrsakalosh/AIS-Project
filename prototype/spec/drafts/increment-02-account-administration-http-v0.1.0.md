## 4. Operations and payloads

**Admin JSON conventions.** Use the existing `poc_session` cookie. For `POST` and `PUT`, send `Content-Type: application/json` and the authenticated session's `X-CSRF-Token`. Each request body has exactly the listed required fields. Positive IDs and versions are integers in `1..9007199254740991` for this interface. A path ID must contain decimal digits and be in range. Send versions as JSON integers such as `1`. Decimal values, strings and booleans fail validation. Return JSON with `Cache-Control: no-store` for admin data.

`AccountView` is `{id, username, display_name, role, status, version}`. `id` is the stable account ID, `username` and `display_name` are strings, `role` is `client | trainer | reception | admin`, `status` is `active | disabled`, and `version` starts at 1 and increments once per committed role or status change. Display name falls back to username for legacy accounts with no saved name. A client profile update changes only the display name and leaves the role/state version as it was.

**Provisioning fields.** Reuse INC-01 input rules. New usernames are 3–32 lowercase ASCII letters, digits, periods, underscores or hyphens and start with a letter or digit. Check uniqueness case-insensitively across all accounts. Display names are trimmed to 1–80 characters and use the same control-character rules as INC-01. Passwords are 12–128 characters, hashed as supplied with the existing password mechanism. Existing credentials and username spellings remain valid. Keep submitted passwords out of URLs, command arguments, logs, error bodies and responses.

**Common error order.** Check authentication (`401 unauthorized`), role (`403 forbidden`), CSRF on writes (`403 csrf_invalid`), then request validation (`422 validation`), then the listed operation-specific checks. Malformed JSON, invalid path IDs, unknown fields, missing fields and invalid field values use the same sanitized `422`. Application errors use `{"error":{"code":"…","message":"…"}}` and echo no submitted values. Known storage unavailability, including exhausted lock waits, returns `503 storage_unavailable`. Other unexpected failures return sanitized `500 internal_error`. Failed transactions roll back all changes, including session revocations. A transport failure after commit is an uncertain result and uses the reconciliation rule below.

## 5. Rules, repetitions and concurrent actions

- **BR-A01 · One role per account.** Client identities come from INC-01 signup. Administrators provision staff and may move staff between supported staff roles. The chosen role alone grants its listed permissions. All accounts keep their IDs, credentials, usernames, profile and any existing domain references through state changes. Disable is account-specific. Anonymous signup can still create a separate Client with a different free username and no membership. Hard deletion and admin password resets are outside this increment.
- **BR-A02 · Preserve administrative access.** Bootstrap runs only when there is no administrator account. The existence check, username check and insert are one transaction. The first successful bootstrap wins. A repeat or concurrent loser reports an existing administrator. Once bootstrapped, every committed account transition leaves at least one active administrator. Disabling or demoting the last active administrator returns `last_active_admin`. A disabled administrator does not count. A self-change follows the same invariant and revokes the actor's sessions on commit if it disables or changes role.
- **BR-A03 · Preserve future bookings.** A Client with any confirmed reservation on a training with `starts_at > now` cannot be disabled. Use fresh server UTC time after lock acquisition. Cancelled rows and trainings at or before their start do not block disable. The owner can first cancel through the existing eligible cancellation flow, or the administrator can wait until the training starts. Disabling or re-enabling never cancels a booking, rewrites reservation ownership or resets membership validity.
- **BR-A04 · Preserve trainer assignments.** The guard applies once INC-03 introduces an explicit login-to-trainer link. If a linked trainer has any future scheduled training (`starts_at > now`), disabling the trainer or switching away from `trainer` returns `future_training_assignment`. Staff resolve it through the relevant catalog or scheduling flow or wait until start. An account with no explicit link has no assignment conflict. INC-02 retains the existing trainer catalog and training assignments and infers no link from IDs or names. A later link retained for reference can grant trainer access only to an active `trainer` account. The later assignment/link write must recheck eligibility in the same transaction as its change.
- **BR-A05 · Revoke and reauthorize atomically.** Each real disable or role change and its account-wide session revocation commit together. Stale cookies yield `401 unauthorized` on protected JSON, the existing login redirect on protected HTML, and `200` with `user:null` and a fresh anonymous CSRF context on `GET /session`. `POST /login` with a current CSRF context treats disabled credentials like a wrong username/password (`401 invalid_credentials`). Use the current account state and role at session issuance. An earlier login is revoked by a later disable or role change. A login that commits after a role change uses the new role if the presented CSRF context is still valid. A revoked token submitted to login or logout before refreshing the context receives the existing `403 csrf_invalid`. Logout with current CSRF clears the caller's session only and returns `204`, including a repeat with a fresh anonymous context.
- **BR-A06 · Serialize at the write boundary.** Under the same SQLite write transaction, recheck actor session and role, target/version and business invariants before applying account changes. Booking creation, cancellation and own-profile updates also recheck actor authorization at their write boundary. A request queued before revocation cannot write after revocation commits. Protected reads use current access for the snapshot they return. A read authorized before a concurrent revocation can finish afterwards. If booking commits first, a still-future confirmed booking makes disable fail. If disable commits first, booking fails with `401 unauthorized`. If cancellation commits first and clears the last future confirmed row, disable may succeed. Concurrent demotions/disables of the final two admins can leave at most one successful reduction.
- **BR-A07 · Resolve repeats and stale edits.** Username uniqueness is checked inside the write transaction for both staff creation and client signup. Concurrent same-username creates across either channel allow one success and return `username_taken` for the other. For role/state writes, two real edits with the same expected version allow at most one commit. A replay after a real change normally receives `account_changed`. A now-revoked caller receives `401 unauthorized` first. A matching-version no-op returns `200` without a version change or revocation. After a timeout, lost response, or uncertain write result, refresh the account list and reconcile against the username or ID and current state/version. If that read fails, keep the action unavailable until the list reloads. The refreshed list shows current state. It cannot identify which request committed a change.
- **BR-A08 · Preserve persisted data on upgrade.** Use the explicit local migration flow for schema 0.2.0 and support the existing 0.1.1 upgrade path through INC-01. Backfill existing accounts as active at version 1 with their original roles and IDs. Keep credentials, existing eligible sessions, profiles, trainer/room/activity records, memberships, reservation IDs/statuses and foreign-key relationships. An upgrade failure leaves the old database intact, and repeating a successful upgrade has no additional effect. Normal startup and re-initialization of an existing database preserve its contents. The documented explicit demo reset recreates the fixtures and requires bootstrap again. Booking works on an upgraded or freshly seeded database before bootstrap.
