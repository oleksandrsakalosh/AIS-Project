## 1. Scope and ownership

The catalog persists in the existing local SQLite database. Future training references protect catalog entries from deactivation. Payments, notifications and native mobile remain outside this increment.

## 3. Browser and HTTP contract

**Browser.** An active admin can open `GET /admin/catalog` from `/staff`. The Slovak page provides **Tréneri**, **Aktivity** and **Športové priestory** lists, distinguishes active and inactive rows, and offers create, rename and deactivate. Trainer rows show the linked account or unlinked state. The administrator can choose an eligible account, replace an existing link, or clear a link. For a first link to a record with existing assignments, explain that the selected login is being associated with that trainer and their existing assignments. Distinguish identical trainer names by record ID and show the username where a link exists. The user can cancel any unsubmitted form without a write. A visitor or revoked session receives `303 /login`, an active Client receives `303 /schedule`, and active non-admin staff receive `303 /staff`. Redirects carry no catalog or account data. Opening and refreshing the page performs reads only.

**JSON access and errors.** Each new JSON operation requires the current active `admin` session via `poc_session`. Writes require `Content-Type: application/json` and the session's `X-CSRF-Token`, obtained through `GET /session`. Apply the existing INC-02 order of `401 unauthorized`, `403 forbidden`, `403 csrf_invalid` on writes, `422 validation`, then operation-specific checks in the order listed. A disabled or revoked cookie receives `401`. Use `Cache-Control: no-store` for catalog and catalog administration responses. Errors use `{"error":{"code":"…","message":"…"}}` with sanitized messages. Browser feedback is Slovak. Known storage unavailability including exhausted lock waits yields `503 storage_unavailable`. Other unexpected failures yield sanitized `500 internal_error`. A failed transaction rolls back its whole change. A transport failure can occur after commit and follows the reconciliation rules in §4.

**Fields.** `kind` is `trainers`, `activities` or `rooms`. Other kinds, invalid path IDs, malformed JSON, wrong or missing required fields, and extra body fields yield `422 validation`. IDs and versions are positive integers through `9007199254740991`. A path ID uses decimal digits. `expected_version` and non-null `account_id` are JSON integers, with strings, fractional values and booleans rejected. `name` is a JSON string. Reject control characters and invalid Unicode scalar values in the submitted string. Trim leading and trailing Unicode whitespace, normalize to NFC and require 1–80 Unicode code points in the result. Internal spaces are significant. A create requires `request_id`, a UUIDv4 string in canonical lowercase hyphenated form, generated once for an intended creation.

**Responses.** `CatalogEntry` has exactly `id`, `name`, `status` (`active` or `inactive`) and `version`. Trainer entries add `account_id`, a nullable stable account ID. A present ID represents the stored link. For the current account role, status and display label the admin page uses the existing `GET /api/admin/accounts` projection. Show when a stored link is ineffective. If the account list fails to load, show a reload action and keep account selection unavailable until it loads. Other catalog controls can use their own successful reads. Account fields, link IDs and catalog versions are private to the admin interfaces. Authenticated schedule projections show the existing catalog label fields.

## 4. State, retries and simultaneous actions

- **BR-CAT01 · Access.** Server checks apply to HTML and direct JSON access. Recheck actor session and role at the write boundary and authorize reads for the snapshot they return. A read authorized before a concurrent revocation can finish. A queued write whose actor has been revoked fails with `401` if revocation commits first. Catalog administration reveals no participant list, bookings, memberships, credentials or session details. An account picker uses the admin projection and offers active Trainer accounts available to that row. Recheck all restrictions on submit.
- **BR-CAT02 · Identity, names and create repeats (DEC-C11).** An entry's identity is its stable `(kind, id)`. Room names and activity names are unique within their respective kind across active and inactive rows. Compare by full Unicode case folding of the trimmed, NFC-normalized name, then NFC of the result. Trainer records may share a name. Keep any legacy collisions visible and preserve their IDs. An unchanged legacy name is a no-op. A new row or real rename must pass the applicable collision check. Retain create receipts in the local database for its lifetime, including after renames and deactivation. Scope a receipt to `(admin_account_id, kind, request_id)` and store the normalized input name and original response. Replays with current authorization and CSRF return the saved response, which may be older than the list. Two identical concurrent creates with one scoped key save one entry. With different keys, distinct trainer intents can both succeed, while competing room or activity names have at most one winner.
- **BR-CAT03 · Reference protection (DEC-C10 and DEC-C12).** A future reference is a training with `starts_at > now` in server UTC, regardless of reservation count or state. Use fresh time after acquiring the write lock. At the exact start, the training ceases to block. A successful deactivation preserves ID, name, training references and any stored trainer link. Past and started trainings still resolve. Under DEC-C10, a rename updates the current label for existing schedule rows and history while preserving their underlying IDs, assignments and booking states. Under DEC-C12 the proposed lifecycle is `active → inactive` in this increment, with no delete operation or ID reuse. Editing a label alone never reschedules a training or sends a notice.
- **BR-CAT04 · Trainer account ownership (DEC-C02).** A catalog trainer and a login are separate records. Each has at most one stored link to the other, including links retained in an ineffective state. A first link is explicit and may bind an active trainer record with future trainings to an eligible, unlinked, active `trainer` account. Removing or replacing an existing link is blocked if any future training references that trainer record. When eligible, replacement changes both ends of the association atomically. An account already linked elsewhere must be explicitly cleared there first. Deactivation, disable and role changes retain the stored link. It is effective only while the record is active and the linked account is active with role `trainer`. With no future assignment, INC-02 may disable or change the linked account's role under its existing rules. Returning the account to active Trainer status makes a retained link effective if the record is active. An admin may clear an inactive record's link when no future assignment blocks it. Link writes change only the catalog version. Account lifecycle writes change the existing account version and revoke sessions as approved. INC-04 must resolve ownership from current trusted state for every scheduling write.
- **BR-CAT05 · Write ordering and rollback.** Use the same SQLite write transaction boundary as account and booking writes. Check current authorization, target version, applicable labels, current links, eligible account status and fresh future references before committing the mutation. Competing real edits with one entry version allow one change. A later authorized request with that old version receives `catalog_entry_changed`, even if it requests the now-current state. Concurrent attempts to claim one login for two records yield at most one stored link. If an initial link to a trainer with future training commits first, a competing disable or move away from Trainer fails with `future_training_assignment`. If disable or role change commits first, the link fails eligibility. The approved account guard and catalog guard leave no route to remove protection from a future linked assignment. A same-version no-op creates no new version or session changes.
- **BR-CAT06 · Browser recovery.** Disable a form's submit while its request is pending. For a fresh success, show the returned row or reload its list. For a replayed create receipt, use its ID to locate the current row after a reload. On a business refusal show the reason and keep the last loaded row displayed. For deactivation or link protection, explain that an assigned training must start or be resolved through a separately authorized scheduling flow. On stale or uncertain results, refresh the affected list and require a fresh explicit action for a new edit. A failed refresh keeps the affected controls blocked until a read succeeds. After a lost create response, keep the original request ID for that intent. Refresh first and, if the receipt still needs confirmation, allow an explicit retry with the original ID and input, including for identical trainer names. A lost PUT response is reconciled against the current row and version. A read shows current state and cannot prove which PUT committed it. A `401` clears private catalog and picker data and sends the user to sign-in.
- **BR-CAT07 · Upgrade and downstream selection.** The local operator uses the existing explicit `python -m app.migrate [--db <path>]` flow against a supported demo database. Upgrade schema 0.3.0 and preserve earlier supported upgrade paths. Backfill existing catalog entries as active at version 1, with no inferred trainer links on upgrade or fresh seed. Preserve existing IDs, names, trainings, accounts, eligible sessions, memberships, reservations and foreign keys. An absent, foreign, unsupported or unavailable database fails safely with a nonzero exit. Failed migration leaves the previous schema/data intact. A completed upgrade and subsequent rerun exit successfully, with the rerun reporting current. Normal initialization preserves an existing database. Explicit demo reset restores fictional fixtures and clears catalog edits, links and create receipts. Schedule reads resolve by ID regardless of catalog status. INC-04 must offer active entries only for new selection and revalidate activity, room and trainer record status and effective trainer ownership in the same write transaction. If scheduling commits first and creates a future reference, deactivation fails. If deactivation commits first, scheduling must refuse the inactive ID. INC-04 owns the scheduling API and its refusal payloads.
